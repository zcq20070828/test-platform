## 一、功能理解与范围界定

### 1.1 核心业务流程

```
┌─────────────────────────────────────────────────────────────┐
│                      用户登录核心流程                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  用户入口 → 认证方式选择 → 凭证提交 → 后台验证 → 认证结果处理  │
│                                     ↓                       │
│                           会话创建 / 错误反馈                 │
│                                     ↓                       │
│                           登录成功 → 跳转/重定向              │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 支持的登录方式

| 登录方式 | 说明 | 涉及系统组件 |
|---------|------|------------|
| 用户名+密码登录 | 基础认证方式 | 前端、后端认证服务、数据库 |
| 手机号+短信验证码登录 | 无密码认证 | 前端、短信网关（第三方）、后端验证服务 |
| 第三方 OAuth 登录 | Google/GitHub/微信等 | OAuth Provider（第三方）、回调服务 |
| 社交账号快捷登录 | 首次授权后免密 | 社交账号绑定服务 |
| 记住登录（Remember Me） | 长期有效 Token | 前端 Cookie/Storage、后端 Token 服务 |
| 找回密码流程 | 邮箱/手机验证码重置 | 邮件服务（第三方）、密码重置服务 |

### 1.3 安全机制概览

- **密码策略**：长度、复杂度、禁止常见弱密码
- **错误限制**：连续失败触发账号锁定或验证码
- **验证码**：图形验证码 / 行为验证码（防机器人）
- **传输安全**：TLS 1.2+ 强制、HSTS 头
- **会话管理**：HttpOnly / Secure Cookie、Token 过期、并发登录控制
- **暴力破解防护**：速率限制（Rate Limiting）、IP 级别封禁
- **敏感操作验证码**：修改密码、修改手机号需额外验证

## 二、需求清单（修正计数版）

> ⚠️ **V1 错误纠正**：V1 报告声称"22项功能需求"，经核实实际计数为 **27项**，分布如下：

| 类别 | 编号范围 | 需求数量 | 说明 |
|------|---------|---------|------|
| 功能需求（F） | F01 ~ F05 | **5项** | 核心登录/登出/找回等 |
| 安全需求（S） | S01 ~ S07 | **7项** | 密码规则、锁定、加密等 |
| 性能需求（P） | P01 ~ P05 | **5项** | 响应时间、并发、可用性 |
| 兼容性需求（C） | C01 ~ C05 | **5项** | 浏览器/OS/网络/多语言 |
| 无障碍/合规（A） | A01 ~ A05 | **5项** | WCAG/GDPR/特殊字符/极端场景 |

**合计：27项需求（V1 误计为22项）**

### 2.1 功能需求（F）

| 需求ID | 需求描述 | 验收标准 |
|--------|---------|---------|
| F01 | 支持用户名+密码登录 | 输入有效凭证后成功进入系统，显示用户信息 |
| F02 | 支持手机号+短信验证码登录 | 发送验证码后90s内可输入，超时失效 |
| F03 | 支持第三方 OAuth 登录 | 至少支持1种第三方账号，授权后创建/绑定本地账号 |
| F04 | 支持记住登录（Remember Me） | 勾选后 7~30 天内免登录 |
| F05 | 支持安全登出 | 清除会话、Token、Cookie，跳转至首页或登录页 |

### 2.2 安全需求（S）

| 需求ID | 需求描述 | 验收标准 |
|--------|---------|---------|
| S01 | 强制密码强度策略 | 密码≥8位，含大小写字母+数字+特殊字符任2种组合 |
| S02 | 禁止常见弱密码 | 禁止 top 10000 常见弱密码库 |
| S03 | 登录失败锁定机制 | 连续5次失败后锁定账号15分钟，或触发强验证码 |
| S04 | 账号锁定防 DoS 滥用 | 同一 IP 大量触发锁定不导致正常用户无法登录；锁定状态不可通过枚举探测 |
| S05 | 加密传输 | 全站强制 HTTPS（TLS 1.2+），登录接口不允许 HTTP |
| S06 | 会话安全 | Cookie 设置 HttpOnly + Secure + SameSite；Token 有明确过期时间 |
| S07 | 防账号枚举 | 登录失败时统一返回"用户名或密码错误"，不因原因不同返回不同提示 |

### 2.3 性能需求（P）

> ⚠️ **V1 指标纠正**：V1 中"P50≤800ms"对含bcrypt/Argon2加密的登录链路偏宽松，修正如下：

| 需求ID | 需求描述 | 验收标准（修正版） |
|--------|---------|-----------------|
| P01 | 登录接口响应时间 | **P50 ≤ 500ms，P99 ≤ 1500ms**（含密码哈希计算） |
| P02 | 并发登录能力 | 单节点 ≥ 200 QPS（`/api/auth/login` 接口） |
| P03 | 短信验证码接口响应 | P50 ≤ 200ms（含第三方短信网关延迟） |
| P04 | 第三方 OAuth 回调 | OAuth Provider 响应 P99 ≤ 3000ms（含网络延迟容错） |
| P05 | 系统可用性 | 登录服务 ≥ 99.9%（月度停机 ≤ 43.8 分钟） |

### 2.4 兼容性需求（C）

| 需求ID | 需求描述 | 验收标准 |
|--------|---------|---------|
| C01 | 浏览器兼容性 | Chrome/Edge/Safari/Firefox 最近2个主版本 |
| C02 | 移动端兼容性 | iOS Safari 15+、Android Chrome 110+ |
| C03 | 网络容错 | 弱网（3G 1.5Mbps）下登录可用；超时合理处理 |
| C04 | 多语言/Unicode | 支持中文/英文/日文用户名，支持 Emoji 等特殊字符 |
| C05 | 极端字符测试 | `' " < > & ; \r \n \0` 等注入字符在用户名/密码中正确处理 |

### 2.5 无障碍/合规需求（A）

| 需求ID | 需求描述 | 验收标准 |
|--------|---------|---------|
| A01 | WCAG 2.1 AA 合规 | 登录表单满足键盘可操作、屏幕阅读器可读、对比度≥4.5:1 |
| A02 | GDPR 合规 | 登录日志不记录明文密码；用户可查看/导出/删除个人登录记录 |
| A03 | 个人信息保护法合规 | 登录行为数据保留不超过必要期限（通常≤6个月）；注销后数据删除 |
| A04 | 多语言无障碍 | 表单标签、错误提示、占位符均有对应语言翻译 |
| A05 | 极端用户场景 | 支持色盲模式、高对比度模式、放大200%下布局正常 |

**用例编号：TC-S01-001（密码强度验证）**

**用例编号：TC-S04-001（账号锁定防 DoS 滥用）**  
**前置条件**：攻击者意图通过反复触发锁定来实施 DoS；存在正常用户账号 `victim_user`  
**测试步骤**：  
1. 从同一攻击源 IP（如测试 IP `203.0.113.50`）对目标账号 `victim_user` 连续输入错误密码5次，触发锁定  
2. 同时，正常用户 `victim_user` 从不同 IP `198.51.100.10` 尝试登录  
3. 观察系统是否因为锁定机制而阻止了正常用户的登录  
4. 从攻击源 IP 继续尝试30次错误登录（超过正常使用频率10倍）  
5. 记录系统对攻击源 IP 的行为（是否封禁 IP 而非仅锁定账号）  
**测试数据**：攻击IP=`203.0.113.50`，正常用户IP=`198.51.100.10`，目标账号=`victim_user`  
**预期结果**：正常用户从不同 IP 仍可登录（锁定针对账号而非IP，但IP级别有独立速率限制）；系统应同时在 IP 级别实施速率限制，避免单 IP 耗尽大量账号的锁定资源  
**关联需求**：S04  
**⚠️ 风险缓解**：此测试揭示了"锁定机制本身可被滥用为 DoS"的高风险场景

---

**用例编号：TC-S07-001（防账号枚举）**  
**前置条件**：系统存在账号 `existing_user`，不存在账号 `nonexist_user`  
**测试步骤**：  
1. 输入不存在的用户名 `nonexist_user`，输入任意密码 `Test@1234`，提交登录  
2. 记录系统返回的错误信息  
3. 输入存在的用户名 `existing_user`，输入任意密码 `Test@1234`，提交登录  
3. 记录系统返回的错误信息  
4. 对比两次错误提示是否完全一致  
**测试数据**：用户名1=`nonexist_user`，密码1=`Test@1234`；用户名2=`existing_user`，密码2=`Test@1234`  
**预期结果**：两次登录失败返回的错误提示**完全一致**，均提示"用户名或密码错误"，不因"用户名不存在"或"密码错误"而给出不同提示  
**关联需求**：S07  
**⚠️ 安全风险**：若返回"用户名不存在"或"邮箱未注册"等不同提示，攻击者可枚举系统中已注册的用户

**用例编号：TC-S05-001（MITM 中间人攻击防护）**  
**前置条件**：测试环境可配置 HTTP（明文）流量捕获；系统已部署 HTTPS  
**测试步骤**：  
1. 配置浏览器使用测试代理（如 Burp Suite）  
2. 将登录请求拦截，修改协议为 HTTP 明文请求  
3. 尝试提交登录表单  
4. 同时检查登录接口是否设置了以下安全响应头：  
   - `Strict-Transport-Security: max-age=31536000`  
   - `X-Content-Type-Options: nosniff`  
   - `X-Frame-Options: DENY` 或 `SAMEORIGIN`  
   - `Content-Security-Policy`（防止 XSS）  
5. 检查请求是否强制重定向到 HTTPS  
**测试数据**：正常登录凭证（测试账号）  
**预期结果**：HTTP 请求被拒绝或强制重定向到 HTTPS；`Strict-Transport-Security` 头已设置；敏感 Cookie 设置了 `Secure` 属性  
**关联需求**：S05  
**⚠️ 风险**：未配置 HSTS 或未强制 HTTPS 时，用户在公共 WiFi 环境下可能被 MITM 攻击截获明文密码

**用例编号：TC-S06-001（会话安全 Cookie 验证）**  
**前置条件**：用户已登录成功，使用浏览器开发者工具或抓包工具  
**测试步骤**：  
1. 登录成功后，在浏览器开发者工具 → Application → Cookies 中查看登录相关 Cookie  
2. 检查每个 Cookie 的属性：  
   - `HttpOnly`：是否设置为 true（防止 JavaScript 读取）  
   - `Secure`：是否为 true（仅在 HTTPS 下传输）  
   - `SameSite`：是否设置为 `Strict` 或 `Lax`  
   - `Expires/Max-Age`：是否设置了过期时间  
3. 在 `Storage` 面板检查 Token/AccessToken 是否存储在 localStorage/sessionStorage
