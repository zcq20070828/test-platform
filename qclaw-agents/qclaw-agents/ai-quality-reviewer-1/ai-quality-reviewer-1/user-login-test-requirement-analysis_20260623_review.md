## 各维度详细分析

### 维度一：事实准确性（22/25）

**评价**：报告引用的技术标准、行业规范整体准确，无重大事实错误。扣分点如下：

| # | 问题描述 | 影响程度 |
|---|---------|---------|
| F1 | **验证码错误 HTTP 状态码使用 400**：`2.2.4 判定表法` 中组合 2/4/6/8 均将"验证码错误"映射为 `400 Bad Request`。然而在多数生产实践中，验证码校验属于"业务层校验异常"，RESTful API 规范中更倾向于使用 `422 Unprocessable Entity`，`400` 通常用于请求格式/语法错误。**判定表与 2.3 接口测试策略中的状态码标准存在不一致**，建议统一。 | 中 |
| F2 | **"错误次数阈值 5 次"边界条件表述模糊**：`2.2.2 边界值分析法` 中将"错误 4 次/5 次/6 次"列为边界值，组合 3（S03 场景）描述为"连续 5 次输错密码 → 账号临时锁定"。此处需明确：第 5 次错误输入后是否立即触发锁定（即阈值是否含第 5 次），还是错误计数器在第 5 次已满、第 6 次才锁定？边界值测试点（4/5/6 次）与场景描述的"连续 5 次"存在语义歧义，建议补充明确逻辑。 | 低 |
| F3 | **密码策略字段未标注来源**：报告第 1 章"密码最小长度 6 位/最大长度 20 位"、第 4 章测试数据均提及具体密码策略数值，但未注明该策略是来自需求文档还是行业标准（如 GB/T 39786-2021 信息系统密码应用要求等）。作为测试需求分析报告，应标注需求来源，以确保测试设计有据可依。 | 低 |
| F4 | **Redis 用于 Session/Token 缓存**：第 3.2 节推荐 Redis 6+ 作为 Session/Token 缓存，技术方向合理。但若系统使用 JWT 无状态 Token，则无需 Redis 存储。此处未区分 JWT 方案 vs. 有状态 Session 方案，存在假设不一致。 | 低 |

**优点**：
- JWT exp 字段定义（access_token ≤ 30min, refresh_token ≤ 7天）符合业界最佳实践
- OAuth 2.0 CSRF state 参数机制描述准确
- 等价类划分表、判定表行列组合计算正确（2³ = 8）
- 缺陷等级映射合理，Urgent/VeryHigh/High/Medium/Low 五级划分标准清晰

**评价**：报告整体逻辑链条清晰，各章节引用关系基本一致。主要逻辑瑕疵如下：

### 维度三：安全性（20/25）

**评价**：报告安全测试覆盖面广，涵盖 OWASP Top 10 相关内容，OAuth 专项测试矩阵尤为完整。主要安全问题如下：

| # | 问题描述 | 风险等级 |
|---|---------|---------|
| S1 | **限流（Rate Limiting）测试缺失**（对应 L1）：暴力破解防护测试未明确测试"限流机制"，包括：单 IP 请求频率限制、账号维度限流、全局限流，以及限流触发后的响应（HTTP 429 Too Many Requests）。限流是抗暴力破解的基础防线，建议补充专项测试项。 | 高 |
| S2 | **登录竞态条件未覆盖**：并发场景下存在竞态风险，例如：① 两个请求同时用正确密码登录同一账号（多点登录 vs. 互斥登录）；② 暴力破解中，第 5 次错误和第 6 次错误同时到达时的计数器行为。报告仅在性能测试中提及并发，未覆盖登录业务层的竞态安全问题。 | 中 |
| S3 | **JWT "kid"（Key ID）注入漏洞未提及**：`2.4.4` 覆盖了"alg: none"攻击，但 JWT 标准头中的"kid"字段若由用户可控输入构造，可能导致密钥混淆攻击（Key Confusion Attack），在部分 JWT 库中危害等同 alg 篡改。建议补充测试用例：尝试在 JWT header 中注入自定义 kid 值并观察服务端行为。 | 中 |
| S4 | **登录日志中 Token 泄露风险**：报告在日志脱敏要求（4.3）中对 Token 处理描述为"测试Token仅用于测试环境，不可复用至生产"，但未明确测试"生产日志中 access_token / refresh_token 是否被明文记录"。若 Token 被写入日志，将导致 Token 完全泄露，建议补充此项测试验证。 | 中 |
| S5 | **密码复杂度策略测试覆盖不足**：`2.4.1` 表格中密码相关测试仅关注传输加密，未覆盖"密码复杂度强制策略"本身的功能测试（长度不足被拒绝、缺少大写字母被拒绝等），这是登录功能的核心测试点之一。 | 低 |

**优点**：
- OAuth 2.0 state 参数 CSRF 防护测试矩阵非常完整（10 项）
- 越权访问测试覆盖水平越权、垂直越权、未授权访问、IDOR 四个维度
- Token 签名校验测试覆盖了 alg: none 攻击
- CSRF Token 测试设计合理，与 OAuth state 区分明确
- 错误信息统一提示（防用户枚举）贯穿多个章节
